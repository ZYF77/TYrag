# 设备管理系统联调优先分阶段实施计划

> 状态：本地联调验收完成；客户真实依赖和生产化事项按本文 DEFERRED 保留
>
> 本计划用于替代“一次性完成全部架构收口”的执行方式。当前目标是先让设备管理系统能够稳定完成文件入库和知识问答联调；认证简化和生产化增强后置。固定解析 profile、Transient Attachment 和独立 Console 纳入本阶段，但不得阻塞文件/问答主链的并行推进。

## 0. 计划目标

本阶段只验证并修复最短业务闭环：

```text
设备管理系统 Backend
  → Enterprise Gateway
  → FILE_SHARE v3 文档登记
  → 固定解析 profile 下的真实解析、Chunk、Index
  → 文档状态轮询
  → 正式 v2 Conversation / Ask
  → History / Citation
```

本阶段同时交付两个旁路能力：

- Transient Attachment 按 OpenAPI v2.1.0 正式公开并完成可运行验证，不作为 FILE_SHARE 主链的替代入口；
- Enterprise Console 使用现有公开 Gateway 能力提供联调诊断入口，其故障不得影响文件、会话和问询 API。

最终验收以设备管理系统开发人员能够只看公开协议和 Postman Collection 完成上述闭环为准，不以“实现了多少架构优化项”为准。

本计划与[《设备管理系统联调可运行版本实施计划》](./设备管理系统联调可运行版本实施计划.md)的关系是：前者保留已经完成的联调基线和既有契约，本文重新划分“必须先跑通”和“后续再优化”的范围。两份文档出现冲突时，以当前 Git commit、当前代码、当前契约和新产生的验收证据为准，不能只依据历史文档宣称通过。

## 1. 执行前冻结的事实和约束

### 1.1 事实来源

执行开始时必须记录：

- 当前 commit、branch 和 working tree 状态；
- 当前实际可访问的 Gateway、RAGFlow、Redis/Valkey、Enterprise DB、FILE_SHARE root 和 Asset Registry；
- 当前实际使用的文档接口、会话接口、认证方式和状态字段；
- 当前 Integration runner、Postman Collection 和协议文档是否真的调用 FILE_SHARE v3 + formal v2；
- 当前测试使用 Asset Registry Stub 还是真实服务。

历史文档中的“已完成”“已通过”“planned”都只能作为调查线索，不能替代本次运行证据。

### 1.2 本阶段契约冻结

本阶段继续使用当前已经存在的契约和认证，不在联调过程中切换认证模型：

- 文件登记和状态：当前 FILE_SHARE v3 契约；
- 会话、问询、历史、citation：当前 formal v2 契约；Attachment 采用保持 `/enterprise/api/v2` 路径兼容的 OpenAPI v2.1.0 additive 契约；
- 设备文件服务认证：现有 HMAC integration identity；
- 用户问询认证：现有 User JWT；
- RAGFlow service account：继续作为 Gateway 到 RAGFlow 的内部实现，不暴露给设备管理系统。
- `equipmentId` 与 `fixedAssetNo`：按一对一业务关系处理；Asset Registry 仍是身份权威，Gateway 不从文档 metadata 猜测映射；同一 tenant 内冲突映射必须 fail closed。
- parsing profile：由服务端固定 profile 名称与版本，设备管理系统不能按请求覆盖 parser/OCR/embedding 等内部参数。
- Transient Attachment：用户已选择方案 A，本阶段提升为 OpenAPI v2.1.0 正式公开能力，冻结 create/ticket/download 和稳定错误码；仍保持 conversation scoped、`indexPolicy=never` 和 TTL 边界。

API Key + `externalUserId`、OIDC/JWT 生产接入和 HMAC/JWT 迁移，本阶段只做事实记录和风险登记，不作为联调前置条件。

### 1.3 修改边界

本阶段允许的最小修改范围：

- `docs/`：联调说明、验收报告和跳过项记录；
- `enterprise/scripts/**`、`enterprise/postman/**`：修正 runner、Postman 和测试环境说明，使其调用最终联调接口；
- `enterprise/tests/**`：补充本阶段必要的契约、权限和 E2E 断言；
- `enterprise/gateway/**`：仅允许为一对一关系、固定解析 profile、Transient Attachment 和现有主链阻塞项做最小修复；
- `enterprise/web/**`：新增独立 Console 页面、公开 API client 和对应测试；
- 必要时对现有 Enterprise 路由做阻塞联调的最小修复。

以下内容默认不修改：

- RAGFlow upstream 核心、官方迁移、根依赖锁文件和公共 Compose；
- Enterprise 数据库模型和正式 migration（若一对一约束无法在现有 Asset Registry 解析边界落实，停止并提交决策项）；
- 认证体系的整体替换；
- 大范围删除或重命名现有 v1/v2/v3 路由；
- 新增独立基础设施或 Service Registry。

如果必须修改共享契约、数据库模型或上游代码，先提交独立的 Change Request/ADR，由 Lead 决定，不在联调修复中顺手完成。

## 2. 本阶段完成标准

### 2.1 必须完成

1. 本地测试环境可以重复启动，且测试前置能够明确区分“配置缺失”和“服务故障”。
2. 设备模拟器只使用公开 Gateway 接口，不调用 RAGFlow 内部接口。
3. FILE_SHARE 文档登记能够返回可用于后续状态查询的业务定位信息；如果现有响应没有稳定 `statusUrl`，只有在客户端无法依据正式契约轮询时才做一个 additive 最小修复。
4. 测试 PDF 从文件服务器进入真实解析、Chunk、Index，并通过真实检索召回。
5. 正式用户能够创建会话、提问、同会话续问、读取历史和 citation。
6. 未授权用户或其他 tenant 无法读取、追加或通过 citation 访问他人的会话和文档。
7. Gateway 重启后，文档状态、会话、消息和 citation 不因进程内存丢失。
8. Postman Collection、Environment template 和联调协议不包含 secret、token、Cookie 或完整连接串。
9. 必须通过的测试不能用 `skip`、`xfail`、删除断言或假造报告绕过。
10. 结果明确标注使用 Stub 还是客户真实依赖；使用 Stub 时只能称为“本地联调基线通过”。
11. 同一 tenant 内 `equipmentId` 与 `fixedAssetNo` 必须一对一解析；任一标识缺失、冲突、跨 tenant 或映射漂移时稳定拒绝，且不得用文档 metadata 自建 alias。
12. 文件入库必须使用服务端固定、可版本化且可读回验证的 parsing profile；客户端不能覆盖 parser/OCR/embedding；profile 未执行或读回不一致时不得标记可检索。
13. Transient Attachment 在正式 Console/联调入口中可见，并验证 conversation ownership、租户隔离、大小/MIME、TTL、一次性下载票据与 `indexPolicy=never`；Attachment 失败不得影响 FILE_SHARE 文档主链。
14. Enterprise Console 可独立访问并展示本阶段联调所需的服务、文档、会话、citation 和 Attachment 诊断；Console 只调用公开 Gateway API，Console 构建或运行失败不得改变后端 API 行为。

### 2.2 本阶段不要求

- 认证方案从 HMAC + JWT 切换为 API Key + `externalUserId`；
- 生产 OIDC/SSO、客户真实 JWKS 和客户真实 Asset Registry 验收；
- 为设备/固定资产一对一关系新增 Enterprise 正式 schema migration；本阶段优先在 Asset Registry 权威解析和 Gateway fail-closed 校验边界落实；
- 全面删除 `EQ-` 历史数据或重写所有旧 fixture；
- 更换 OCR 厂商、embedding 模型或重构 RAGFlow parser；本阶段只固定现有可运行 profile 名称、版本和应用验证；
- 全面 Prompt Injection 防护工程；
- Service Registry 和生产级可观测平台；
- Webhook、RAGFlow 多副本、Redis HA、PostgreSQL repository 和高级 agent/memory。

这些事项必须在验收报告中列为 `DEFERRED`，不能写成已解决，也不能阻塞当前单实例联调闭环。

## 4. 分阶段执行计划

### T0：基线核对，禁止改代码

调查内容：

- 当前真实路由和认证：文件接口用 HMAC，用户接口用 JWT，是否存在 legacy/demo 路径；
- 当前 FILE_SHARE v3 和 formal v2 是否真的被 runner/Postman 使用；
- 当前状态接口是否能表达解析完成、索引完成、质量门和可检索性；
- 当前 conversation ownership、citation ACL 和重启持久化；
- 当前 Asset Registry 是 Stub 还是真实服务；
- `EQ-`、`equipmentId`、`fixedAssetId` 是否会破坏真实设备 ID；
- 当前是否存在绕过 Gateway 的测试上传或 RAGFlow 写入口。

验收证据：

- `docs/integration/` 下的事实记录或本计划的执行记录；
- 当前 route/auth/data-flow matrix；
- working tree 无未经确认的修改；
- 明确列出阻塞项和“不需要为联调修改”的事项。

### T1：启动现有测试环境和测试身份

优先复用现有 Compose、runner、Postman 和 HMAC/JWT 配置，不新增 API Key 体系。

至少验证：

- Gateway health；
- RAGFlow API 和必要的 worker；
- Enterprise DB；
- Redis/Valkey replay store；
- FILE_SHARE 只读 root；
- Asset Registry Stub 或真实 endpoint；
- Gateway 到 RAGFlow 的内部调用；
- 测试 HMAC integration identity 和测试 User JWT。

验收标准：

- preflight 将每个依赖标为 `configured/healthy/unavailable`；
- 缺少外部环境时返回 blocked，不得伪造 pass；
- HMAC secret、JWT、API key 等敏感值不出现在日志、终端、Postman 导出或 artifact；
- 进程重启后仍能重新执行 preflight。

### T2：E2E-01 文件入库主链

使用非敏感测试 PDF，执行：

```text
文件服务器测试目录准备 PDF
→ HMAC POST FILE_SHARE v3 document register
→ 使用正式状态接口轮询
→ Gateway 通过只读挂载读取文件
→ RAGFlow 真实解析、Chunk、Index
→ 质量门和当前版本判定
→ 真实检索命中测试文档
```

必须断言：

- `equipmentId` 和现有业务元数据未被 Gateway 擅自改写；
- 外部文档版本、SHA-256、路径坐标和登记幂等关系一致；
- 文件登记不会要求设备管理系统调用 RAGFlow 内部 API；
- 状态接口的 `retrievable` 只有在真实查询准入条件满足时才为 true；
- citation 能回到外部文档 ID、版本和可解释的位置；
- 文件不存在、路径逃逸、文件变化、重复登记、RAGFlow 失败均有稳定结果。
- `equipmentId` 与 `fixedAssetNo` 由 Asset Registry 解析为同一且唯一的 canonical identity；一对一冲突不得进入解析队列；
- 服务器实际应用固定 parsing profile 名称与版本，且 `parserApplication.state=executed`、`readbackMatch=true` 后才可能通过质量门；
- 请求体中出现 parser、OCR provider、embedding 或 profile override 时按现有契约拒绝或忽略，并有明确测试证明不能改变服务端固定配置。

如果当前代码只能跑通 S3/v1/demo 路径，先将其记录为阻塞，不得把旧路径当作设备正式联调通过；修复只限于让现有 FILE_SHARE v3 主链可运行。

### T3：E2E-02 会话和权限主链

使用现有 User JWT 和两个测试用户执行：

```text
User A 创建正式 conversation
→ 第一次 ask
→ 同 conversationId 第二次 ask
→ 读取 history
→ 打开 citation/source
→ Gateway 重启
→ 恢复同一 conversation
```

User B 和其他 tenant 必须验证：

- 不能 list/get User A 的 conversation；
- 不能追加 User A 的消息；
- 不能读取 User A 的历史；
- 不能读取 User A 的 citation/source；
- 不能通过修改 equipment context 绕过 ACL。

本阶段不重构用户身份系统，但 ownership/ACL 失败属于联调阻塞问题，必须最小修复或明确阻塞，不得用共享 RAGFlow service account 作为放宽 Enterprise 隔离的理由。

### T4：Transient Attachment 可见与可运行

在不替代 FILE_SHARE 持久文档入口的前提下验证现有 v2 Attachment：

- Console 和联调说明中保留入口，不通过默认 501 或纯隐藏菜单宣称完成；
- attachment 只属于指定 tenant/user/conversation，`indexPolicy=never`，默认 TTL 24 小时；
- 上传大小、MIME、对象完整性、一次性下载票据、过期和清理均有正负向测试；
- User B、其他 tenant、归档或不存在的 conversation 不得创建或下载；
- Attachment 服务不可用或清理失败不能改变 FILE_SHARE 文档和正式问询接口的可用性。

已完成决策：采用方案 A，由 Lead 将主 OpenAPI 升为 v2.1.0 并冻结 create/ticket/download 与 Attachment 稳定错误码；W3 只负责使运行时和测试符合该契约，不得自行新增或漂移公开语义。

### T5：Enterprise Console 独立交付

Console 作为独立并行工作包，优先复用现有 `enterprise/web`、health、文档状态、conversation/history/citation 和 Attachment API：

- 页面能区分配置缺失、服务不可用、未授权、处理中、可检索和失败；
- 不展示 secret、Token、Cookie、完整 Prompt、原始模型响应或内部 RAGFlow 标识；
- 不允许浏览器直连数据库、Redis、对象存储管理端口或 RAGFlow 内部 API；
- Console 的 API client 只调用公开 Gateway 路由，超时和局部失败不得造成整页不可用；
- Console build/test 独立执行，不纳入 Gateway 进程启动的硬依赖。

### T6：联调材料和对外边界

复用并校对现有 `enterprise/postman/**` 和 `docs/integration/**`：

- Collection 只包含最终设备系统需要的公开接口；
- 不要求设备系统传 `datasetId`、RAGFlow document ID、parser、embedding、systemPrompt、role、ACL 等内部字段；
- 认证、轮询、错误码、幂等和状态字段与真实运行结果一致；
- secret-free Environment template 中敏感字段为空；
- 协议明确当前使用 HMAC + JWT，并说明 API Key/OIDC 尚未纳入本阶段；
- 协议明确使用轮询，不把 planned Webhook 写成已实现；
- 真实 Asset Registry 尚未接入时，文档明确标注 Stub 边界。
- 协议明确 equipment/fixed asset 一对一、服务端固定 parsing profile、Transient Attachment 当前边界和 Console 非后端依赖。

验收证据：

- Postman artifact 静态校验；
- 至少一次使用最终 Collection 的 smoke run；
- 文档中的每个示例响应都能在当前实现中找到依据；
- 导出文件不包含 secret。

### T7：回归和封版

执行顺序：

1. Contract profile；
2. P0/offline profile；
3. Enterprise web 现有测试和 TypeScript 检查（如本次没有前端修改，只记录基线结果）；
4. Integration preflight；
5. E2E-01；
6. E2E-02；
7. Postman/Newman smoke；
8. Transient Attachment contract/integration/ACL/TTL 测试；
9. Enterprise Console TypeScript、Vitest 和 build；
10. Git diff、secret scan、RAGFlow upstream change guard。

封版条件：

- 必须测试全部通过，或每个失败都有明确的 blocked/deferred 原因；
- 不能把外部服务不可用写成业务测试通过；
- 不能把 Stub 结果写成客户正式依赖通过；
- 不提交 `tmp/` 下无效测试内容、失败日志、运行截图或含环境信息的临时 artifact；
- 报告列出本次实际修改、未修改项、契约变化、剩余风险和后续任务。

## 5. 验收 Gate 和证据矩阵

| Gate | 通过条件 | 必须留存的证据 | 不通过时处理 |

## 7. 风险和停止条件

出现以下情况时停止扩大范围，先报告事实：

- 真实 FILE_SHARE v3 主链无法启动，但修复需要修改 RAGFlow upstream 或官方数据库模型；
- 当前公开契约和真实代码不一致，且修复会破坏已有正式消费者；
- equipment/fixed asset 一对一必须依赖新 migration、客户数据回填或改变 Asset Registry 正式契约；
- 固定 parsing profile 必须修改 RAGFlow upstream、官方数据库模型或绑定尚未确认的 OCR/embedding 供应商；
- 无法证明 conversation ownership，或需要大规模迁移现有会话；
- 需要读取未确认环境的 secret；
- 测试只能依靠 mock/skip/xfail 才能通过；
- 当前工作区出现不属于本任务的用户修改；
- 任何失败日志、artifact 或 Postman 文件包含 secret、Cookie、完整 Prompt 或原始模型响应。

此时应输出 blocker、影响、最小替代方案和是否需要 Lead/用户决策，不应自行扩大为架构重构。
