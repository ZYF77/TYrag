# 07 检索、问答、会话与引用

## 1. 查询类型

Gateway 将问题分类为：

- `document_knowledge`：文档解释、操作步骤、故障排查；
- `business_fact`：设备属性、最近维修、保养记录；
- `hybrid`：同时需要文档和业务事实；
- `unsupported_precise_query`：尚未配置的统计或自由 SQL；
- `unsafe_or_unauthorized`。

分类可由规则优先，LLM 仅作为辅助，不能绕过权限和查询白名单。

## 2. 文档检索流程

```text
原问题
→ 提取设备号/故障码/文档类型
→ 计算 ACL 和当前版本条件
→ 调用 RAGFlow retrieval/chat
→ Rerank/父子上下文由 RAGFlow 处理
→ Gateway 复核文档与引用
→ 回答模型或流式转发
```

设备码和故障码必须保留原文，同时进行规范化变体，例如 `AX-200`/`AX200`。是否修改 RAGFlow tokenizer 必须由评测证明；优先使用查询增强和 metadata 条件，不先改底层检索引擎。

## 3. 回答约束

- 只根据已授权证据和业务查询结果回答；
- 无可靠证据时明确未找到；
- 区分“文档要求”和“实际业务记录”；
- 不将模型隐藏推理返回前端；
- 故障流程保留前置条件、分支和安全警告；
- 精确日期、次数和状态以业务数据库为准；
- 回答应携带可追溯来源；无可靠证据时通过 `NO_RELIABLE_EVIDENCE` 显式返回，不视为成功回答；
- 消息业务状态（`completed` / `no_reliable_evidence` / `failed`）与 `citations` 证据数据相互独立，不互相推导；
- 禁止用 `citations` 是否为空推导消息状态，也禁止用消息状态推导 `citations`。

无可靠证据时，Gateway 返回 `NO_RELIABLE_EVIDENCE` 且消息状态为 `no_reliable_evidence`；RAGFlow Session 不可读时返回 `CONVERSATION_UNAVAILABLE`，不得用空本地记录冒充历史消息。

`NO_RELIABLE_EVIDENCE` 响应建议保持 HTTP 200，返回明确拒答正文；正常响应按运行结果显式返回业务 `status`，`citations` 由检索结果独立映射。

## 4. 引用统一模型

```json
{
  "sourceType": "document|business_record",
  "sourceId": "...",
  "title": "...",
  "externalDocumentId": "...",
  "sourceVersionId": "...",
  "pageNo": 37,
  "bbox": {"x1": 0.1, "y1": 0.2, "x2": 0.8, "y2": 0.4},
  "assetId": "...",
  "excerpt": "...",
  "recordType": "maintenance",
  "recordId": "..."
}
```

客户端不得自行提交或修改 externalDocumentId、sourceVersionId、pageNo、bbox、assetId 和业务 recordId。v1 的 `documentId/versionId` 仅作兼容别名，v2 只返回上述外部字段。

## 5. 会话真相源

MVP 默认：RAGFlow Session 保存 RAGFlow 侧上下文；正式 API 在企业库 `ext_conversation_message` 持久化消息正文与业务状态，并在 `ext_conversation_citation` 保存消息级 Citation Snapshot。历史读取不依赖 RAGFlow Session 可用性。

```text
ext_conversation（正式）
- tenant_id
- business_conversation_id
- business_user_id
- ragflow_chat_id
- ragflow_session_id
- equipment_id
- fixed_asset_no
- current_fault_code
- status
- created_at
- last_message_at

ext_conversation_message
- conversation_id
- tenant_id
- business_user_id
- message_id
- role
- status（completed / no_reliable_evidence / failed）
- content
- citations_json
- ragflow_message_id
- created_at / updated_at

ext_conversation_citation
- citation_id
- message_id
- conversation_id
- document_id / ragflow_document_id / chunk_id
- source_version_id / asset_id
- title / page_no / bbox_json / excerpt
```

`ext_conversation_map` 继续仅供 demo 入口使用；正式 API 不对外暴露 RAGFlow chat/session id。

## 6. 多轮上下文

每轮请求都重新验证：

- 当前用户；
- 会话归属；
- 当前设备权限；
- 设备是否已切换；
- 文档版本和状态。

设备上下文切换必须显式写入会话映射。不能因为上一轮提到设备 A，就在用户无权访问时继续召回 A。

v2 创建后唯一的持久 context mutation 是
`PATCH /enterprise/api/v2/conversations/{conversationId}/context`。省略字段表示不变，
null 表示清除；有效变化令 `contextVersion` 加一。equipmentId、fixedAssetNo、
assetId 必须通过设备管理系统 Asset Registry 解析；文档 metadata 不能创建 alias。
Gateway 保存 canonical snapshot，消息路径在 5 分钟 TTL 后惰性刷新；Registry 不可用返回
`ASSET_REGISTRY_UNAVAILABLE`，重新绑定到另一设备返回 `CONVERSATION_CONTEXT_STALE`。
没有 canonical equipment 的 draft conversation 不能发送消息（`CONVERSATION_CONTEXT_REQUIRED`）。
实际 retrieval document set 固定为 `ACL ∩ canonical equipment snapshot ∩ active/current ∩ quality passed`；
message DTO 不接受设备或故障字段作为一次性 override。

## 7. SSE

v1 兼容流式接口为：

`POST /enterprise/api/v1/conversations/{conversationId}/messages:stream`

请求头携带 `Accept: text/event-stream` 或查询参数 `stream=true` 时返回 SSE；否则返回 JSON。事件格式：

v2 正式入口为
`POST /enterprise/api/v2/conversations/{conversationId}/messages`，只以
`Accept: text/event-stream` 选择 SSE，否则返回 JSON。SSE 直接消费 RAGFlow
`chat_completion_stream()`，不把完整答案伪造成一条 delta。请求必须携带
`clientMessageId`，并严格选择 question 或 suggestion 分支之一。

```text
event: run.started
data: {"conversationId":"...","runId":"...","replayed":false}

event: answer.delta
data: {"conversationId":"...","content":"..."}

event: citation
data: {Citation}

event: answer.completed
data: {"conversationId":"...","messageId":"...","status":"completed|no_reliable_evidence","citations":[...]}

event: run.failed
data: {"conversationId":"...","code":"...","message":"..."}
```

结束条件：

- 正常完成：`answer.completed`（上游必须已收到终止帧）；
- 上游失败：`run.failed`，不发送 `answer.completed`；
- 客户端断开：停止写流，尝试关闭上游连接，durable run 持久化为 `failed`，绝不可标记为 `completed`；重复请求不会自动重跑。

重复请求在原 run 仍为 `running` 时返回 202 和相同 `runId`，即使客户端要求 SSE 也返回状态 JSON；租约过期固定为 `RUN_INTERRUPTED`。

## 8. 正式 API

v1 兼容入口（均为 `BearerAuth`，非 demo 路由）：

| 方法 | 路径 | capability |
|---|---|---|
| POST | `/enterprise/api/v1/conversations` | `list_sessions` |
| GET | `/enterprise/api/v1/conversations/{conversationId}` | `list_sessions` + `view_citations` |
| POST | `/enterprise/api/v1/conversations/{conversationId}/messages:stream` | `ask` + `view_citations` |
| GET | `/enterprise/api/v1/citations/{citationId}` | `view_citations` + `list_sessions` |

创建会话返回 Gateway 自有 `conversationId`，不返回 RAGFlow session id；RAGFlow 映射仅存在于 `ext_conversation` 内部。

v2 正式入口增加 cursor list、独立 messages page、context、archive 和 rules-based
suggestions；完整 wire 以 `contracts/integration-openapi-v2.yaml` 为准。会话状态只有
`active|archived`，archive 后历史/citation 可读但 context/message 不可写。

## 8.1 Conversation / Message 生命周期

- 创建会话：`POST /conversations` 建立企业会话，owner/tenant 写入 `ext_conversation`，RAGFlow session 按需延迟创建；
- 发送消息：先持久化 user message，再执行 RAGFlow，完成后持久化 assistant message 与 Citation Snapshot；
- 历史读取：`GET /conversations/{conversationId}` 直接返回持久化消息与快照，不依赖 RAGFlow Session 可用性；
- 消息终态：`completed` / `no_reliable_evidence` / `failed`，由运行结果显式决定，不随 citation 数量推导；
- 同一会话的并发 ask 使用 conversation 级串行，保证消息顺序稳定。

## 9. ACL 三层防线

1. Gateway 身份与 capability；
2. 检索前通过 `FormalScopeResolver` 编译 `AclScope`，仅 `sync_status=ready`、`quality_status=passed`、ACL 允许的文档进入 RAGFlow `doc_ids` 预过滤；
3. 返回 Citation 前再次校验文档 ACL。

正式查询不读取 `demo_document_acl`，ACL 事实来自 `ext_document_map.department_id / security_level / allow_group_ids / deny_group_ids`。

## 10. Citation Snapshot

assistant message 完成时，把 citation 按消息持久化到 `ext_conversation_citation`。历史读取和 Citation API 均使用快照字段；即使当前文档映射已升级到 v2，历史 citation 仍保持 v1 的 `versionId` / `assetId`。

## 11. 错误模型

正式错误使用 `contracts/error-codes.yaml` 中的稳定 code；新增 `CITATION_NOT_FOUND`、`DOCUMENT_NOT_READY`、`RAGFLOW_SCOPE_VIOLATION`。RAGFlow 内部错误统一映射为 `RAGFLOW_UNAVAILABLE` 或 `RAGFLOW_API_INCOMPATIBLE`，不泄漏内部 URL、traceback 或 API Key。

## 12. Phase 2 正式 E2E

Phase 2 正式 E2E 全部由仓库内已提交脚本驱动，不依赖未提交 runner：

```powershell
python enterprise/scripts/run_wp04_phase2_e2e.py
```

前提是已部署 RAGFlow v0.26.4（`9380`）与 MinIO，并提供运行环境：

```text
RAGFLOW_API_KEY 或 RAGFLOW_ADMIN_EMAIL + RAGFLOW_ADMIN_PASSWORD
S3_ENDPOINT
S3_ACCESS_KEY
S3_SECRET_KEY
S3_BUCKET（可选，缺省按 run 创建临时 bucket）
```

runner 负责：清空旧 doc_ids trace、启动 Gateway（进程内 Uvicorn 文件日志）、
等待健康、执行 `enterprise/scripts/wp04_phase2_e2e.py`、停止本轮 Gateway。
每次运行使用独立的 SQLite 文件（`artifacts/wp04-phase2-e2e-<时间戳>.db`），
避免上一次运行的 ready 映射污染本轮“未 ready 不可查询”断言。
WP-03 deterministic sample PDFs 缺失时，runner 会自动调用已提交的
`enterprise/scripts/wp03/generate_samples.py` 生成到
`artifacts/wp03/samples/`；这些是本地 E2E artifacts，不会提交 Git。
无需人工先执行任何隐藏前置步骤。
本地验收证据写入 `artifacts/`（JSON artifact、SQLite、trace、Gateway log），
均不提交。

transport 证据区分两段：

- `transportFailureStage=pre_stream_chat_lookup`：整个 RAGFlow 不可达时，正式
  ask 在 `_ensure_chat` 的 `list_chats()` 失败，SSE 返回 `run.failed`；
- `streamTransportFailureVerified=true`：`enterprise/scripts/wp04_stream_transport_probe.py`
  用真实本地 socket 在 `/api/v1/chat/completions` 建立连接后中途断开，真实执行
  `RagflowClient.chat_completion_stream()`，断言映射为 `RAGFlowAPIError`、
  无 `NameError`、错误内容不泄漏 API Key；E2E 再启动指向该 fault server 的
  Gateway，走正式 `messages:stream` 并断言 `run.failed` 且绝不
  `answer.completed`。

ACL 证据来自 Gateway 真实写入的 `ENTERPRISE_QUERY_TRACE_DOC_IDS` trace：
`authorizedRagflowDocIdsSent` 必须等于授权文档，`unauthorizedRagflowDocIdsSent`
与 `missingAuthorizedRagflowDocIds` 均为空，`ragflowDocIdsScopeLeakFree=true`。
