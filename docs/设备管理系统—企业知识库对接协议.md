# 设备管理系统—企业知识库对接协议

> 适用版本：FILE_SHARE API v3.1.0 / FILE_SHARE callback v1.0.0 / Query API v2
>
> 状态：本地测试开发环境已通过 E2E；客户正式环境仍需替换正式 SSO/JWKS、网络和文件服务器后验收。第一阶段入库与问询均信任 EAM 提交的设备标识，不依赖独立 Asset Registry 服务。
> 事实来源：当前 Enterprise Gateway 实现、`contracts/file-share-v3.yaml`、`contracts/file-share-callback-v1.yaml`、`contracts/integration-openapi-v2.yaml` 和已通过的 Postman/Integration 验收。

## 1. 系统边界

设备管理系统只调用 Enterprise Gateway 的公开 EAM 接口，不直接调用 RAGFlow、Redis、Enterprise DB 或任何 Gateway 内部接口。

本版本文件接入方式唯一确定为 FILE_SHARE：设备管理系统先把不可变 PDF 保存到双方约定的外部文件服务器，再向 Gateway 提交文件坐标、SHA-256 和业务元数据。设备管理系统不向 Gateway 上传 PDF 二进制。

```text
设备管理系统文件服务器
→ POST /enterprise/api/v3/documents（202 瘦身受理回执）
→ Gateway/RAGFlow Parse、Chunk、Index、质量门
→ Gateway 终态回调 POST 到设备系统（retrievable/failed/review_required）
→ POST /enterprise/api/v2/conversations
→ POST /enterprise/api/v2/conversations/{conversationId}/messages
→ answer + citations
```

旧 `/enterprise/api/v2/documents` S3 坐标入口只用于历史兼容，不是新设备系统的推荐入口。

## 2. Base URL 与内容类型

本机测试默认 Base URL：

```text
http://127.0.0.1:5188
```

设备系统运行在其他主机时，由部署方提供可访问的 Gateway 地址；不得将 RAGFlow、Redis 或文件服务器管理端口直接暴露给设备系统。

除 citation 原 PDF 外，请求和响应均使用 `application/json`。时间字段使用带时区的 ISO 8601 字符串。

## 3. Authentication

### 3.1 文件登记与状态：HMAC Integration Identity

以下 v3 请求只接受 HMAC，不接受用户 JWT 或 legacy Service Bearer Token：

- `POST /enterprise/api/v3/documents`
- `GET /enterprise/api/v3/documents/sync-status`
- `GET /enterprise/api/v3/documents/{externalDocumentId}/status`

请求头：

```http
X-TY-Timestamp: <10 位 Unix 秒>
X-TY-Key-Id: <测试环境 key ID>
X-TY-Signature: v1=<小写十六进制 HMAC-SHA256>
```

签名输入为以下五行，最后一行后不追加换行：

```text
v1
<timestamp>
<大写 HTTP method>
<规范化 path 与按键值排序的 RFC3986 query>
<精确 raw body 的 SHA-256 小写十六进制>
```

签名密钥绑定一个明确的 `(tenantId, sourceSystem)`。时间窗口为 ±300 秒；成功验签后的 replay key 保留 10 分钟。重试业务请求时必须生成新的 timestamp/signature，但保持业务幂等标识不变。

测试密钥由部署方通过安全渠道提供，只放在 Gateway 进程和 Postman Local Vault/未同步本地 Environment 中，不得写进请求 body、源码、导出的 Collection 或 Git。

### 3.2 会话、问询和 citation：User JWT

正式 v2 用户接口使用：

```http
Authorization: Bearer <user JWT>
```

JWT 必须通过 Gateway 配置的 issuer、audience、签名和有效期验证，并映射到 active Enterprise 用户。测试用户至少需要 `end_user` role，以及与文档匹配的 tenant、department、groups 和 security level。

生产环境应使用正式 SSO/JWKS；本地 HS256 Token 仅用于测试开发环境。

## 4. FILE_SHARE 文件登记

### 4.1 请求

```http
POST /enterprise/api/v3/documents
Content-Type: application/json
Accept: application/json
X-TY-Timestamp: <timestamp>
X-TY-Key-Id: <key-id>
X-TY-Signature: v1=<signature>
```

```json
{
  "eventId": "evt-device-manual-001",
  "eventType": "upsert",
  "tenantId": "<tenant>",
  "sourceSystem": "EAM",
  "externalDocumentId": "DEVICE-MANUAL-001",
  "sourceVersionId": "v1",
  "sha256": "<64 位 PDF SHA-256>",
  "fileName": "device-manual.pdf",
  "mediaType": "application/pdf",
  "source": {
    "kind": "FILE_SHARE",
    "storageRootId": "device-share",
    "relativePath": "manuals/device-manual.pdf",
    "size": 123456,
    "etag": "<可选的文件版本标识>"
  },
  "metadata": {
    "schema_version": 1,
    "tenant_id": "<tenant>",
    "external_document_id": "DEVICE-MANUAL-001",
    "source_system": "EAM",
    "equipment_id": "EQ-001",
    "fixed_asset_no": "FA-001",
    "document_type": "PRODUCT_MANUAL",
    "document_version": "v1",
    "department_id": "maintenance",
    "security_level": 2,
    "allow_group_ids": ["maintenance"],
    "deny_group_ids": [],
    "business_status": "active",
    "page_count": 10
  }
}
```

约束：

- `mediaType` 只能是 `application/pdf`；
- `fileName` 不能包含目录分隔符；
- `relativePath` 必须位于服务端配置的 `storageRootId` 根目录内；
- body 与 `metadata` 中的 tenant、source、external document 和 version 必须一致；
- PDF 在登记后必须保持不可变；文件大小、mtime、etag 或 SHA-256 变化会失败；
- `document_type` 由 EAM 维护并直接传递；服务端只校验非空且不超过 64 个字符，不限制具体名称。

### 4.2 202 响应

FILE_SHARE `3.1.0` 登记响应为瘦身受理回执，不再返回 `statusUrl` 或进度字段：

```json
{
  "operationId": "evt-device-manual-001",
  "externalDocumentId": "DEVICE-MANUAL-001",
  "sourceVersionId": "v1",
  "deduplicated": false,
  "updatedAt": "2026-08-11T06:00:00+00:00"
}
```

`202` 只表示 Gateway 已原子接收任务，不表示文件已经可检索。终态结果由 Gateway 主动回调设备系统（见 §13）。

## 5. 文件任务状态

### 5.1 查询单个版本（诊断）

正式对接以终态回调为主。GET status 保留给 Console/运维诊断：

```http
GET /enterprise/api/v3/documents/{externalDocumentId}/status?tenantId=...&sourceSystem=...&sourceVersionId=...
X-TY-Timestamp: <new timestamp>
X-TY-Key-Id: <key-id>
X-TY-Signature: v1=<signature for exact path/query>
```

### 5.2 查询任务列表

```http
GET /enterprise/api/v3/documents/sync-status?tenantId=<tenant>&sourceSystem=EAM&limit=20
```

列表响应：

```json
{
  "items": [
    {
      "externalDocumentId": "DEVICE-MANUAL-001",
      "sourceVersionId": "v1",
      "status": "ready",
      "pipelineStatus": "DONE",
      "parseCompleted": true,
      "indexCompleted": true,
      "qualityStatus": "passed",
      "retrievable": true,
      "errorCode": null
    }
  ]
}
```

实际 item 包含与单状态响应相同的完整字段。

### 5.3 状态解释

| 字段 | 含义 |
|---|---|
| `status` / `stage` | Gateway 当前阶段，例如 `received`、`registered`、`parsing`、`ready`、`failed` |
| `pipelineStatus` | RAGFlow 公开 readback 状态，例如 `UNSTART`、`RUNNING`、`DONE`、`FAIL` |
| `parseCompleted` | parser 配置/执行 readback 已验证 |
| `indexCompleted` | RAGFlow 明确报告 `DONE` |
| `qualityStatus` | 当前质量门结果 |
| `retrievable` | 文档具备进入检索候选集的条件；用户请求仍会再次执行 ACL |
| `readiness.blockingReason` | `retrievable=false` 时的稳定阻塞原因 |
| `errorCode` / `error` | 失败时的稳定错误代码、消息和 retryable |

设备系统只有在 `retrievable === true` 后才能认为该文件已可用于问询。不要仅判断 HTTP 200、`status=ready` 或 `pipelineStatus=DONE`。

测试建议每 2 秒轮询一次，最多 120 次；生产轮询频率和总时长由双方部署参数另行确认。

## 6. 创建会话

```http
POST /enterprise/api/v2/conversations
Authorization: Bearer <user JWT>
Content-Type: application/json
```

```json
{
  "equipmentId": "EQ-001",
  "fixedAssetNo": "FA-001",
  "faultCode": "FAULT-001"
}
```

Gateway 直接信任并保存 EAM 提交的 `equipmentId` / `fixedAssetNo`，不调用 Asset Registry 或 EAM GET 做身份回查。设备身份一致性由 EAM 负责。没有 `equipmentId` 的草稿会话不能问询（`422 CONVERSATION_CONTEXT_REQUIRED`）。

成功响应 HTTP 201（v2.2+ 含开场 `suggestions`）：

```json
{
  "conversationId": "<conversation-id>",
  "title": "New conversation",
  "status": "active",
  "equipmentId": "EQ-001",
  "fixedAssetNo": "FA-001",
  "faultCode": "FAULT-001",
  "contextVersion": 1,
  "lastMessageAt": "2026-08-11T06:00:00+00:00",
  "createdAt": "2026-08-11T06:00:00+00:00",
  "context": {
    "equipmentId": "EQ-001",
    "fixedAssetNo": "FA-001",
    "faultCode": "FAULT-001",
    "contextVersion": 1,
    "registryVersion": null
  },
  "suggestions": [
    {
      "suggestionId": "inspect-fault",
      "label": "检查当前故障",
      "displayPrompt": "请根据可靠文档说明当前故障的检查步骤。",
      "contextVersion": 1,
      "expiresAt": null
    }
  ],
  "contextCompacted": false
}
```

`suggestions` 由 Gateway 服务端定义；客户端展示后以 `suggestionId` + 匹配的 `contextVersion` 发消息，不得自定义 chip prompt。`PATCH .../context` 后旧 suggestion 返回 `409 SUGGESTION_STALE`。User JWT 由 EAM 签发、Gateway 验签；EAM 不直接调用 RAGFlow。

## 7. 提交问题与续问

### 7.1 JSON 回答

```http
POST /enterprise/api/v2/conversations/{conversationId}/messages
Authorization: Bearer <user JWT>
Accept: application/json
Content-Type: application/json
```

自由提问：

```json
{
  "clientMessageId": "device-message-001",
  "question": "请说明该设备的维护步骤。"
}
```

点选开场选项：

```json
{
  "clientMessageId": "device-message-002",
  "suggestionId": "inspect-fault",
  "contextVersion": 1
}
```

成功响应 HTTP 200：

```json
{
  "conversationId": "<conversation-id>",
  "clientMessageId": "device-message-001",
  "runId": "<run-id>",
  "messageId": "<assistant-message-id>",
  "answer": "<answer>",
  "status": "completed",
  "citations": [
    {
      "citationId": "<citation-id>",
      "sourceType": "document",
      "title": "device-manual.pdf",
      "externalDocumentId": "DEVICE-MANUAL-001",
      "sourceVersionId": "v1",
      "pageNo": 1,
      "bbox": null,
      "assetId": "FA-001",
      "excerpt": "<evidence excerpt>",
      "recordType": null,
      "recordId": null
    }
  ],
  "replayed": false
}
```

消息业务状态只有 `completed`、`no_reliable_evidence` 或 `failed`。业务状态与 citation 数量相互独立，客户端不得根据 citation 是否为空自行改判状态。

同一会话续问时保持相同 `conversationId`，但每个新问题使用新的 `clientMessageId`。EAM 不发送 RAGFlow `session_id`。长对话时 Gateway 可透明滚动摘要；`conversationId` 与消息历史原文不变。

### 7.2 真 SSE

同一路由设置：

```http
Accept: text/event-stream
```

事件顺序为 `run.started`，零到多个 `answer.delta` / `citation`，最后 `answer.completed` 或 `run.failed`。没有第二个 `:stream` 路由。

## 8. 会话和历史恢复

```http
GET /enterprise/api/v2/conversations?limit=20
GET /enterprise/api/v2/conversations/{conversationId}
GET /enterprise/api/v2/conversations/{conversationId}/messages?limit=20
Authorization: Bearer <user JWT>
```

列表使用 opaque cursor，响应结构为：

```json
{
  "items": [],
  "nextCursor": null,
  "hasMore": false
}
```

消息历史按创建时间正序返回 user/assistant 消息、原始业务状态和已授权 citation。归档后的会话和历史仍可读，但不能继续写入。

## 9. Citation 与原文件定位

### 9.1 Citation 详情

```http
GET /enterprise/api/v2/citations/{citationId}
Authorization: Bearer <user JWT>
```

Gateway 会校验 citation 所有者和当前文档 ACL。无权访问返回 403 或不泄露资源存在性的 404。

### 9.2 原 PDF

```http
GET /enterprise/api/v2/citations/{citationId}/source
Authorization: Bearer <user JWT>
Accept: application/pdf
Range: bytes=0-1023
```

- 无 Range 时返回 200；
- 合法单 Range 返回 206、`Content-Range`、`Accept-Ranges: bytes` 和 `ETag`；
- 非法或多 Range 返回 416；
- 文件在登记后变化返回 409 `DOCUMENT_SOURCE_CHANGED`；
- 该接口返回 PDF 字节，不返回文件服务器路径。

## 10. 幂等规则

文档业务键是 `(tenantId, sourceSystem, externalDocumentId, sourceVersionId)`。

| 场景 | 结果 |
|---|---|
| 相同 `eventId` + 相同 normalized payload | 202，原 operation，`deduplicated=true` |
| 相同 `eventId` + 不同 normalized payload | 409 `EVENT_ID_CONFLICT` |
| 相同业务键 + 新 eventId + 相同 SHA-256 | 202，已有资源，`deduplicated=true` |
| 相同业务键 + 不同 SHA-256 | 409 `DOCUMENT_VERSION_CONFLICT` |

消息幂等范围是同一 conversation 内的 `clientMessageId`：相同 payload 重放原结果，不同 payload 返回 409 `CLIENT_MESSAGE_ID_CONFLICT`。正在执行的重复请求返回同一 `runId` 和 202，不启动第二次执行。

## 11. 错误响应

统一 JSON envelope：

```json
{
  "code": "DOCUMENT_SOURCE_NOT_FOUND",
  "message": "Document source is unavailable",
  "requestId": "<request-id>",
  "retryable": true
}
```

常用错误：

| HTTP | code | 含义 |
|---:|---|---|
| 401 | `AUTH_SIGNATURE_INVALID` / `AUTH_REPLAY_DETECTED` | HMAC 非法或请求重放 |
| 401 | `AUTH_TOKEN_INVALID` | User JWT 非法或过期 |
| 403 | `AUTH_BINDING_DENIED` / `ACL_DENIED` | tenant/source binding 或用户 ACL 拒绝 |
| 404 | `DOCUMENT_NOT_FOUND` / `CONVERSATION_NOT_FOUND` / `CITATION_NOT_FOUND` | 资源不存在或不可见 |
| 409 | `EVENT_ID_CONFLICT` / `DOCUMENT_VERSION_CONFLICT` | 幂等或不可变版本冲突 |
| 409 | `DOCUMENT_SOURCE_CHANGED` | 登记后的外部 PDF 已变化 |
| 409 | `CLIENT_MESSAGE_ID_CONFLICT` | 同消息 ID 使用了不同 payload |
| 416 | `RANGE_NOT_SATISFIABLE` | citation source Range 非法 |
| 422 | `DOCUMENT_METADATA_INVALID` / `VALIDATION_ERROR` | 请求或 metadata 不符合契约 |
| 422 | `DOCUMENT_SOURCE_NOT_FOUND` / `DOCUMENT_HASH_MISMATCH` | 外部文件缺失或摘要不一致 |
| 503 | `RAGFLOW_UNAVAILABLE` | 问答/解析依赖暂时不可用 |
| 503 | `AUTH_REPLAY_STORE_UNAVAILABLE` | Redis replay store 不可用，认证 fail closed |

客户端只根据 `retryable` 和双方约定的退避策略自动重试；不要对所有 4xx/5xx 无条件重试。

## 12. 超时与终态通知

- 文件登记是异步 `202` 受理回执；HTTP 202 不是处理完成；
- FILE_SHARE `3.1.0` 起，设备系统以 Gateway 终态回调为主路径，不再依赖登记响应中的 `statusUrl`；
- GET status 仅供 Console/运维诊断；本地联调 Collection 可使用诊断轮询等待 `retrievable`；
- 每次 HMAC 请求使用新的 timestamp/signature；
- 模型问询耗时可能长于普通状态查询，客户端超时应由部署双方明确配置；
- 超时后可使用同一 `clientMessageId` 查询/重放稳定 run，而不是生成重复业务消息；
- `retryable=false` 的冲突、权限或 schema 错误必须先修正请求。

## 13. Webhook / 终态回调

FILE_SHARE `3.1.0` 提供 Gateway → 设备系统 的终态回调（`contracts/file-share-callback-v1.yaml`）。

- 回调 URL 仅来自服务端 `sourceSystem -> endpoint` 配置；登记请求禁止 `callbackUrl`；
- 终态枚举：`retrievable` / `failed` / `review_required`；
- 使用独立 outbound HMAC secret 签名；2xx 确认成功，其余按 1/5/30/120/600 秒退避最多 8 次后死信；
- 回调失败只影响投递状态，不回滚已成功的 ingestion。

交付文件：

- `enterprise/postman/tyrag-device-integration.postman_collection.json`
- `enterprise/postman/tyrag-local.postman_environment.template.json`

Collection 已验证以下最小链路：登记（瘦身受理回执）、重复登记、诊断状态轮询到 `retrievable`、非法 HMAC、缺失文件、未登记状态、创建会话、两轮问询、历史、citation 详情/source 和非法 JWT。不能只以 HTTP 200 判断成功，Collection 同时断言状态、标识和 citation。

## 15. 接口版本策略

- 文件接入契约：`/enterprise/api/v3`，当前 FILE_SHARE contract `3.1.0`；
- 终态回调契约：`contracts/file-share-callback-v1.yaml` `1.0.0`；
- 会话与问询契约：`/enterprise/api/v2`，当前 contract `2.0.0`；
- 向后兼容的可选字段可以 additive 发布；删除字段、改变字段含义、认证方式或幂等规则必须发布新版本；
- 服务端内部 RAGFlow ID、ticket 和存储路径永不属于外部契约；
- v2 S3 文档入口保留兼容，但新设备系统不得同时实现两种文件入口。

## 16. 当前验收声明

当前代码已在本地测试开发环境证明：设备管理系统模拟方只通过公开 Enterprise Gateway 契约即可完成“外部文件服务器 PDF 入库”和“同一会话两轮知识问答”两条链路，无需了解或直接调用 RAGFlow 内部 API。

该声明不覆盖生产部署、正式 SSO/JWKS、客户网络、防火墙、真实文件服务器权限和多 Gateway 高可用；这些在生产前必须单独验收。第一阶段不要求独立 Asset Registry HTTP API。
